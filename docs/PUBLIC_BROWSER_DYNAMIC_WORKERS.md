# Public Browser: dynamically reconciled owner-bound worker manifest

Status: source-only, feature default **off**, not deployed or approved for general public access. Requires the prior verified public operator and peer-authenticated provisioning IPC. It does not create containers or provide a cross-tenant-safe CDP/Steel relay.

`COMMANDCORE_BROWSER_DYNAMIC_WORKERS_ENABLED=false` is the default. Setting it true additionally requires OAuth Browser enabled, an operator-owned worker manifest, a valid owner binding key, an Ed25519 attestation **public** key, and the existing allow-hosts list. The API must never be given Docker socket, host operator signing seed or credentials from the private deployment.

`RefreshingOwnerBrowserWorkerPool` starts from a validated read-only manifest, allowing an empty initial list and adds/removes worker entries after the operator atomically publishes a new manifest. It fails closed for missing, symlinked, insecure, oversized, or changed-while-reading files. The historical routes and owner binding ledgers must remain under operator control; the API should have only read-only access. Identity/route matches may preserve an already verified in-memory session; any worker removal/replacement invalidates its sessions and human handoff tokens. Every action still requires operator Ed25519 physical proof both before and after the operation, and a post-action manifest check denies returning output when the worker changed while awaiting network data.

This code is not a general solution to the source feature's current risk: dynamically adding a worker does not make its Docker control network accessible to the API, and a flat shared network is **not** an acceptable substitute. An independently reviewed tenant-isolated proxy relay must enforce the same OAuth owner binding and prove the selected immutable worker route at both ends. The API also needs validated JWT-derived provision calls, operator-side admission quotas, durable job acknowledgment, lifecycle restart/cleanup reconciliation, idle expiry, and real two-account Auth0+ChatGPT review. Until then, **do not enable the dynamic flag or public Browser**. Keep the existing private Browser path intact and deploy shared source with separate, least-privilege public/private secrets.

Tests are synthetic, do not use real accounts or start containers: two owner manifests, immutable ledger session preservation, removal invalidation, permission and symlink rejection, and a changed-during-action screenshot suppression. Perform live canary with isolated reviewer accounts and a rollback before claiming parity.
